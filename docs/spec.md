# hubblerc 기획

hubble의 Claude Code 환경. mod(함수 훅) + skill + 훅 + 에이전트를 플러그인 하나(`plugins/hubblerc`)에 담아 이 맥, 회사 스튜디오, 집 미니에서 같이 쓴다.

- 기준 빌드: Claude Code 2.1.308 (mod API는 early access라 버전마다 바뀔 수 있음)
- 방향: 일을 편하게 만드는 도구 + 내 취향대로 꾸미기, 둘 다
- 표시: [확인] 타입 정의·실행으로 확인함 / [추정] 아직 확인 안 함

## 결정한 기능 (v0.1 범위)

### F1. 상태 밴드: claude-hud 대체
작은 모니터용. 프롬프트 바로 위 3줄(`AbovePrompt`).

구현된 모습 (2026-10-26):
```
Opus 5.5 · xhigh │ ctx ━━━━──── 45% │ 5h ━━────── 25% ↻1h30m │ 7d 12% │ hubblerc main*
◐ Bash 테스트 실행 12s +1 │ ◐ Explore: 인증 코드 찾기 2m15s │ ▸ 인증 버그 수정 2/5
직전 2m13s · 파일 +24 −3 · Read 5 · Bash 2
```
3줄은 effort 슬라이더가 열리면 `effort  1: low  2: med  3: high  4: xhigh  5: max  0: 엔진 설정`으로 바뀐다.

- 1줄(항상): 모델·effort(auto 여부), 컨텍스트 %, 5시간 한도 %와 리셋까지 남은 시간, 7일 한도, 프로젝트 이름·브랜치·미커밋(*). 폭이 모자라면 7일 → 프로젝트 이름 → 막대 그래프 순으로 덜어낸다. 비용은 기본 숨김. 모델이 바뀌면(`/model`을 치거나 고름, `/config`, 자동 전환) 엔진의 `classic.PostModelSwitch` 뒤 바로 상태를 다시 읽어 30초를 기다리지 않는다(2026-11-06).
- 2줄: 실행 중 도구(Bash는 용도), 서브에이전트(종류·설명·경과), 할 일 진행. 대기 중에도 줄을 유지하고 할 일 또는 "대기 중"을 보여준다(높이 고정).
- 3줄: 직전 답변 요약.
- 스타일(2026-10-26, 두 번째): 배경색 없이 터미널 기본 글자색을 쓰고, 색은 필요한 곳에만 터미널 색 이름(green/yellow/red/cyan/magenta/blue/gray)으로 칠한다. 그러면 터미널 테마(사용자는 Orca 다크 + Kanagawa)가 색을 정한다. 막대는 얇은 선(`━━━━────`)이고 채운 부분이 사용률 단계색(초록 → 60% 노랑 → 85% 빨강), 숫자는 60% 이상일 때만 색. 라벨과 구분선은 흐리게, 브랜치는 magenta, 미커밋 `*`는 yellow, effort는 cyan(세션 고정이면 yellow + `(세션)`). 상태바형 배경은 가독성이 나빠서 버림.
- 간격: 밴드 위에 빈 줄 하나. 밴드 아래 빈 줄은 엔진의 알림 자리("Update installed …")라 줄일 수 없다(음수 여백으로 당기면 3줄이 가려짐 [확인]).
- effort 슬라이더(2026-10-26 결정): `ctrl+x ctrl+e`(또는 1줄의 effort 값 클릭)로 3줄 자리에 `effort 1: low 2: med 3: high 4: xhigh 5: max 0: 엔진 설정`이 열린다. 숫자 하나로 고르면 이 세션에 적용되고 닫힌다. 다시 `ctrl+x ctrl+e`, 10초 경과, 다음 질문 시작 때도 닫힌다. Esc로는 닫을 수 없다: Esc는 입력창(엔진)이 먼저 받고, 버튼에는 조합키만 연결되며, 밴드가 키보드를 놓을 때 알려 주는 이벤트도 없다 [확인: 타입 문서]. Esc로 닫히는 건 패널(`closeOnEscape`)뿐인데, 전체 화면에서는 사이드 패널로 열려서 밴드 슬라이더를 택했다(2026-10-26). 숫자 핫키 버튼은 열려 있을 때만 존재한다(빈 입력창에서 숫자를 치면 밴드 버튼이 눌리는 엔진 동작을 이용).
  - 단축키: mod는 키 바인딩을 직접 만들 수 없다. effort 버튼에 엔진 동작 이름 `app:cycleDiffBase`(diff 패널용)를 붙이고, `~/.claude/keybindings.json`의 Chat 문맥에 `ctrl+x ctrl+e` → 그 동작을 등록했다(원래 외부 편집기 키. 외부 편집기는 `ctrl+g`로 계속 열린다). 거쳐 온 키: `Option+E`(meta+e)는 macOS에서 악센트(´) 입력 키라 터미널이 단축키로 보내지 않았다 [확인]. `ctrl+x e`는 한글 입력 상태에서 `e`가 `ㄷ`으로 조합 중에 붙잡혀 있다가 다음 키(백스페이스 등)를 칠 때 넘어가서, `ctrl+x ㄷ`을 묶어도 한 박자 늦게 열렸다 [확인]. 컨트롤 조합은 입력기를 거치지 않으므로 단일 키 `ctrl+q`, `ctrl+t`(할 일 목록 키를 풀고)로 바꿔 봤지만 둘 다 반응이 없었다 [확인]. 공식 문서상 `ctrl+q`는 막힌 키가 아니고 키 설정은 재시작 없이 반영된다. 원인은 입력창이 단일 컨트롤 키를 먼저 가져가는 것으로 본다 [추정: 셸 편집키로 `ctrl+t`는 글자 바꾸기, `ctrl+q`는 문자 그대로 넣기]. 두 키 모두 컨트롤인 조합 `ctrl+x ctrl+e`는 한글 상태에서도 열고 닫힌다 [확인, 2026-10-26]. diff 패널이 열려 있을 때만 이 키가 원래 동작을 한다. 이 파일은 플러그인에 들어가지 않으므로 기기마다 등록해야 한다.
  - 패널 닫기 `ctrl+x ctrl+x`(2026-11-05 추가): 엔진의 패널 닫기 `ctrl+x x`도 한글 입력 상태에서 두 번째 키 `x`가 `ㅌ`으로 조합 중에 붙잡혀 듣지 않았다(사용자 보고). effort 키와 같은 이유라 같은 해법으로, 키 설정의 `Pane`과 `PaneField` 문맥(패널, 또는 그 입력칸이 키보드를 가졌을 때)에 `"ctrl+x ctrl+x": "pane:close"`를 더한다. 엔진 기본 `ctrl+x x`는 그대로 둔다. 동작·문맥 이름과 기본값 [확인: 공식 문서 code.claude.com/docs/en/keybindings, 2026-11-05: `pane:close` 기본 Ctrl+X X, `Pane`과 `PaneField` 두 문맥에 적용]. `/setup`의 키 목록이 이제 키마다 문맥을 갖고(`setup.ts`의 `KEYS`), 그 문맥의 블록이 없으면 파일 끝에 새로 만든다. 한글 상태에서 실제로 닫히는지는 화면 확인 전.
  - 엔진의 `Option+P`는 모델 선택까지 함께 열려서, effort만 조정하는 용도로는 쓰지 않기로 했다.
- 수치 출처: `$.session.usage()` = 상태줄과 같은 context / rateLimits(percentUsed, resetsAt) / cost [확인]. 모델 `$.session.model()` [확인]. 서브에이전트 `$.agent.list()`(id, type, description, status; 시작 시각은 없음 → 직접 기록) [확인]. 브랜치는 SessionRepo에 없어서 git으로 읽는다.
- 전환 시점: 개발 중에는 이 폴더에서만 켜지므로 claude-hud(전역 statusLine)를 유지. 배포할 때 statusLine 설정을 뺀다.

### F2. 레이아웃 두 가지 + config
- 큰 모니터: 사이드바(`Pane`). 전체 화면 모드(`tui: fullscreen`, 지금 설정)에서 대화 옆에 붙는다.
- 작은 모니터: F1 밴드
- config `layout: auto | sidebar | band`. auto는 터미널 폭 기준. 엔진은 mod가 스스로 여는 패널을 144칸 이상일 때만 옆에 붙인다 [확인: 문서].
- mod 옵션(`userConfig`)은 `/config` 메뉴 항목이 되고 선택지형도 된다. 값은 기기별 사용자 설정(`pluginConfigs`)에 저장되고 프로젝트 설정은 읽지 않는다 [확인: 디버그 로그]. 그래서 기기마다 다른 레이아웃을 쓸 수 있다.
- 구조: 데이터 수집은 한 곳(`$.state`), 그리는 부분만 사이드바용과 밴드용 두 벌.
- 구현(2026-10-26):
  - 사이드바(패널 id `hubblerc`): 위에 밴드 1줄의 항목을 한 줄씩(모델·effort, ctx, 5h, 7d, 프로젝트·브랜치), 그 아래 지금 실행 중인 것(밴드 2줄), 그 아래 "변경 파일"과 "목차".
  - 변경 파일: 이 세션에서 바뀐 파일 전체(서브에이전트 변경 포함). 저장소 안에 있고 `git status`에 남은 변경이 없으면 커밋된 것으로 보고 흐리게 `✓`를 붙인다. 2026-10-26부터 `git status --ignored`로 넷을 가른다: 커밋됨(흐림 `✓`), 바뀜(밝게, +초록 −빨강), 추적 안 됨(밝게 + `?`, git 기호), `.gitignore`로 무시됨(흐림 + `!`). 폴더째 추적 안 되거나 무시되면 git이 `dir/` 하나로만 알려 주므로 그 아래 파일 전체에 적용한다(전엔 정확히 같은 경로만 봐서 추적 안 된 폴더 안 파일이 `✓`로 보였다, 사용자 지적)(제목에 "커밋 안 됨 N"). git은 파일을 바꿀 수 있는 도구(Edit·Write·MultiEdit·NotebookEdit·Bash, 서브에이전트 것 포함)가 끝난 직후, 질문을 보낼 때, 30초마다 읽는다(2026-10-28 바꿈. 전에는 5초마다와 Claude의 git 명령 직후. `.git`의 HEAD·index·logs/HEAD 엔진 감시는 2026-11-06에 뺐다, 아래 "주기 작업과 자원"). 저장소 밖 파일(메모리, /tmp 등)은 저장소 파일 아래에 폴더별로 모으고, 폴더마다 경로를 얹은 흐린 점선(`┄┄ ~/.claude/…/memory ┄┄┄`) 아래에 흐리게, `✓` 없이 보인다(2026-10-26 결정. 처음 기록은 "표시하지 않는다"였으나 코드는 커밋 안 됨처럼 밝게 보이고 있었다). 경로는 홈을 `~`, macOS의 `/private/tmp`를 `/tmp`로, 길면 가운데를 `…`로 줄인다. 한도: 모두 12개. 바깥 폴더가 먼저 자리를 잡아(폴더당 2개, 폴더 3개까지, 넘는 폴더는 `┄┄ 다른 폴더 N개`) 저장소 파일이 많아도 밀려나지 않고, 저장소 파일은 최소 6개. 넘친 개수는 부분마다 "외 N개"(저장소 파일 아래, 폴더마다 그 아래). "외 N개 더 보기"(또는 "다른 폴더 N개 더 보기")를 누르면 상자가 모든 파일을 보인다. 펼친 동안에는 저장소 파일의 "외 N개"가 있던 자리(저장소 파일과 바깥 경로 선 사이)에 흐린 "줄이기"가 생겨 12개로 돌아간다. 처음엔 목록 맨 아래에만 "접기"를 두었는데 목록이 길면 화면 밖으로 밀렸고(2026-10-26 사용자 지적), 제목 옆과 맨 아래에 함께 둔 안은 과하다고 해서 한 곳으로 정했다. 이 세션만 유지(`$.state.filesExpanded`). 파일 이름은 `file:///<경로>` 링크(`Link`, 경로 조각마다 퍼센트 인코딩)다. 전체 화면에서는 엔진이 클릭된 하이퍼링크를 직접 받아 `file:` 주소(호스트 없음)면 그 파일을 연다 [확인: 실행 파일 코드, 2.1.310]. 대화 속 링크와 같은 처리기다. 전체 화면이 아니면 터미널(Orca, OSC 8 지원)이 연다. 파일별 +/− 누적과 바꾼 답변 번호(`#3 #7`, 최근 4개). 마지막으로 바뀐 파일이 위. 같은 이름이 둘 이상이면 폴더까지 표시. 12개까지 보이고 나머지는 "외 N개".
  - 목차: 답변마다 한 줄(`#번호 질문`, 실패 수, 시간), 최신이 위. 한 페이지 10개, 아래 `◀ 최근  1 2 3  이전 ▶`로 넘긴다(2026-10-26 요청). 누르면 `$.ui.scroll`로 대화를 그 답변으로 옮긴다. 질문 행(`session.append`의 `door: 'prompt'` 행 uuid)이 있으면 질문을 위에(`start`), 없으면(다른 세션 메시지·알림으로 시작한 답변) 답변 끝 줄을 아래에(`end`) 둔다. 행 id가 없는 답변(복원한 답변, 다른 세션 메시지로 시작한 답변)은 `UserMessage` 렌더 때 모아 둔 "질문 문구(`promptKey`) → 행 id" 표로 찾는다. 렌더 중에는 상태를 쓸 수 없어 모듈 메모리에 둔다(리로드 때 엔진이 다시 그리며 채운다 [추정]). 아직 그려지지 않은 행이거나 이동이 거절되면(사용자 스크린샷 2026-11-05: "#1(으)로 이동하지 못했습니다: nothing drawn under that requestId") 예전엔 알림만 띄웠는데, 이제 그 답변을 창으로 보여 준다(아래 답변 창). 테스트 키트는 대화 행 스크롤을 흉내 내지 못해서("no implementation for ui.scroll") 실제 이동은 화면에서 확인한다.
  - 답변 창(2026-11-05 사용자 결정, `hooks/answer.tsx`): 이동 실패 시 새 패널 `hubblerc-answer`를 `{ title: '#N 답변', columns: 사이드바와 같은 56, closeOnEscape: true, focus: true }`로 연다(사람이 누른 것이라 폭과 상관없이 그려진다, 전체 화면에서는 사이드바 옆 탭 [추정: 타입 문서]). Esc나 ✕로 닫힌다. 엔진의 닫기 표시는 패널 틀 줄에 있어 사이드바와 탭으로 같이 열리면 눈에 안 띄어서(사용자 보고 2026-11-05) 본문 맨 윗줄 오른쪽에 흐린 ` ✕ 닫기 ` 버튼을 뒀다(터미널·데스크톱 같음). 누르면 `$.ui.close`로 닫고, Esc로 닫을 때와 같은 정리(답변을 잊고 밴드를 다시 그리게 tick을 올림)를 버튼 쪽에서도 한다(자기 `ui.close` 훅이 자기 닫기를 듣는지와 상관없이). 내용: `#N 질문 전문`, 흐린 한 줄(시간 · 답변 끝 요약 줄과 같은 `summarize`), `[요약 보기]`, 구분선, 답변 본문(텍스트 블록을 이은 것, Markdown 요소로, 없는 화면이면 Text) 앞 200줄과 "외 N줄". 본문은 `$.session.messages({ as: 'api' })`를 resume 복원과 같은 답변 경계 규칙(`restore.ts`의 `answersOf`로 빼서 함께 씀)으로 나눈 뒤, 목차의 답변과 같은 질문(`promptKey`)을 끝에서부터 세어 찾는다(기록은 최근 100개라 앞에서 세면 어긋남). 질문 문구가 없는 답변은 끝에서부터의 자리로. 못 찾으면 "대화 기록에서 이 답변을 찾지 못했습니다". 답변은 모듈 메모리에(본문이 길다), `answerVersion` 상태로 다시 그린다. 리로드하면 잊고 "목차에서 다시 눌러 주세요".

(2) `kind: 'next'` 다음 질문 앞 200자(같은 가림) — 정정·재요청인지는 나중 분석에서. (3) `kind: 'turn'` 그 답변의 도구 실패 수, 답변 시간, 출력 토큰. 다음 질문이 오면 그 판정은 신호를 더 받지 않는다(그 답변이 판정되지 않아도).

- 적용 방식(auto용): `/config`(`$.config`)에는 effort 항목이 없다 [확인: config.list에 model은 있고 effort는 없음]. 엔진 커맨드 `/effort`는 있다 [확인: command.list]. `/effort`는 설정 파일에 저장될 수 있어(미확인) 우선 mod가 `turn.step`에서 이 세션의 요청마다 바꿔 끼우는 방식으로 만든다. `/effort` 동작 확인은 설정 파일을 바꿔야 해서 사용자 허락 후에.
- 울트라코드 표시(2026-10-28 사용자 요청, 0.8.0): 엔진에 새로 생긴 세션 단위 토글(`/effort ultracode on|off`, 엔진 effort 슬라이더의 Tab, 설정 키 `ultracode`). 켜져 있으면 1줄 effort 뒤에 ` · ultracode`(사이드바는 Claude 주황 `claude`, 밴드는 마젠타, 굵게). mod에 상태를 주는 API가 없다 [확인: 실제 세션에서 `/effort ultracode on` 전후로 `config.list`(행 없음: `workflows`·`workflowKeywordTriggerEnabled`·`workflowSizeGuideline`뿐)와 `settings.read`(변화 없음), 렌더 props(SessionMode·PromptHint에 없음), `turn.step` 필드(없음)를 봄]. 그래서 엔진의 `/effort`를 `command.run`으로 받아(인자 없이 슬라이더를 열어도 온다 [확인]) 0.5초·2초 뒤 기록 파일 끝 64KB에서 엔진 출력 줄(`"content":"<local-command-stdout>…`) 가운데 `Ultracode on|off`가 든 마지막 줄을 읽는다. 문장 처음(`Ultracode on (this session only): …`)에도, 슬라이더로 레벨을 바꿔 확정할 때처럼 끝(`Set effort level to high (…): … · Ultracode on`)에도 온다 [확인: 이 세션 기록]. 도구 호출이나 메시지가 같은 글자를 인용한 줄은 따옴표가 이스케이프돼 걸리지 않는다. `/effort high` 같은 레벨 변경은 울트라코드를 그대로 두고 출력에도 안 적는다 [확인]. 인자 없는 `/effort ultracode`는 켜기 [확인]. 이 세션 시작 전 시각의 줄(이어 연 세션의 옛 기록)은 무시. 시작 때는 설정 키 `ultracode`가 true일 때만 켜짐. `--effort ultracode` 실행 옵션과 원격 제어로 켠 것은 못 본다. 실제 세션에서 켜기·슬라이더로 끄기 표시 확인 [확인].

### F8. 새 버전으로 재시작 (2026-10-27, 테스트 통과, 실제 세션에서 `/relaunch` 동작 확인 [확인: 사용자])
장비 상자의 `재시작`(설치됐는데 재시작만 남았을 때)이나 `/relaunch`로, 같은 세션을 새 버전으로 다시 연다. 진행 중인 작업은 끊지 않는다.
- 동작: 누르면 답변·도구·서브에이전트가 모두 없을 때 0.2초 뒤 재시작, 있으면 `재시작 대기`로 바뀌고 2초마다 보다가 끝나는 순간 재시작. 기다리는 동안 다시 누르면(또는 `/relaunch`) 취소. 재시작은 사이드바 기록·세션 effort 선택·auto 여부를 `$.store`의 `restartSnapshot`에 저장 → 세션 id를 `$HUBBLERC_RELAUNCH_FILE`에 적음 → `$.command.run({ command: 'exit' })`. 다시 열리면 `restoreTurns`가 같은 세션 id의 10분 안 스냅샷을 한 번 읽고 지운다(시간까지 살아남음).
- 셸 함수(`plugins/hubblerc/shell/relaunch.zsh`): `claude`를 감싸 `HUBBLERC_RELAUNCH_FILE`(임시 파일 경로)을 넘기고, 끝난 뒤 그 파일에 세션 id(uuid 형식)가 있으면 `claude --resume <id>`로 다시 띄운다. 처음 실행의 `--plugin-dir`·`--plugin-dir-no-mcp`·`--add-dir`·`--settings`·`--setting-sources`·`--mcp-config`·`--strict-mcp-config`·`--model`만 넘기고, 세션을 정하는 옵션과 권한 옵션은 넘기지 않는다. `hcc` 별칭도 이 함수를 거친다. 가짜 `claude`로 확인: 첫 실행 옵션 그대로, 다시 띄울 때 `--plugin-dir`·`--model`만 남고 `--resume <id>`, 임시 파일 지워짐 [확인].
- 셸 함수 없이 띄운 세션(환경 변수 없음)에서는 아무것도 하지 않고 `/setup`을 안내한다.
- 같은 셸 파일이 Orca 그림 값도 넣는다(0.7.1): `TERM_PROGRAM`이 Orca이고 `CLAUDE_CODE_FORCE_TERMINAL_IMAGES`가 정해져 있지 않으면 `1`로 export(이미 정한 값은 0이어도 그대로, Orca와 같은 규칙). 셸이 시작할 때 `~/.zshrc`가 불러오므로 새 탭부터. 그래서 `/setup` 보고의 이름도 "셸 설정(재시작 함수 … Orca 그림)". 기존 설치는 복사본이 배포본과 달라져 세션 시작 때 `/setup` 안내가 뜨고, `/setup`이 새 파일을 복사한다. zsh로 네 경우 확인: Orca·값 없음 → 1, Orca·0 → 0, Orca·1 → 1, ghostty → 없음 [확인].
- 셸 파일 판 번호(2026-10-29): `/setup`은 설치된 셸 파일이 자기 것과 같은지만 봐서, 버전이 다른 세션끼리 서로 덮어썼다. aitop100의 0.7.1 이전 세션이 `/setup`으로 새 파일을 예전 것으로 되돌렸고, hcc 세션이 다시 열리며 "설정 1개가 덜 됐습니다"가 떴다 [확인: 두 세션 기록]. 셸 파일에 `# hubblerc-shell-version: N`을 두고, 설치된 판이 더 크면 설치된 것으로 본다(덮어쓰지도 알리지도 않음). 작으면 덮어쓰고, 같으면 내용이 다를 때 덮어쓴다. 번호 없는 예전 파일은 0. 내용을 바꾸면 번호를 올린다. 이미 배포된 예전 판의 `/setup`은 여전히 덮어쓰므로 모든 세션이 새 판이 되기 전까지는 같은 일이 생길 수 있다.
- 같은 셸 파일의 `hubblerc-key`(2026-11-05, 판 2): likely의 API 키를 키체인 항목 `hubblerc-likely`에 넣고·바꾸고·지우고·확인하는 zsh 함수(F10). `hubblerc-key`(=`status`)는 `security find-generic-password -s hubblerc-likely`의 종료 코드로 있는지만 말하고(`-w`를 쓰지 않아 값이 나오지 않는다), `set`은 `security add-generic-password -U -s hubblerc-likely -a "$USER" -w`(값을 인자로 넘기지 않고 security가 가린 입력으로 두 번 묻는다, `-U`라 있으면 바꾼다), `delete`는 y/N 확인 뒤 `security delete-generic-password -s hubblerc-likely`, 그 밖의 인자는 사용법(종료 코드 2). 판 번호를 2로 올려, 이미 설치한 기기는 다음 세션에 "설정 1개가 덜 됐습니다"가 뜨고 `/setup`으로 새 판이 깔린다. 확인: `zsh -n` 문법 검사, 가짜 `security`를 PATH 앞에 둔 zsh에서 status·set·delete(y/n)·없을 때·잘못된 인자 [확인: 2026-11-05, 실제 키체인은 건드리지 않음]. 테스트 키트는 실제 셸을 띄우지 못해 kit 테스트는 없다.
- 한계: 백그라운드로 돌린 명령(`run_in_background`)은 hubblerc가 보지 못해 기다리지 않고 프로세스와 함께 끝난다. 세션 안에서만 사는 예약 작업도 사라진다 [추정]. `/relaunch` 처리 중에 `/exit`를 바로 부르면 테스트 키트가 거부해서 0.2초 뒤로 미뤘다. mod가 `/exit`를 실행해 끝내고 셸 함수가 다시 여는 흐름은 실제 세션에서 동작했다 [확인: 사용자, 2026-10-27].
- 고른 이유(2026-10-27): 진행 중인 답변은 프로세스 메모리에 있어서 새 버전으로 옮길 수 없다. Orca가 업데이트해도 작업이 안 끊기는 건 셸이 앱이 아니라 따로 도는 `orca-terminal-host`의 자식이고, 업데이트 때 그 호스트는 그대로 두기 때문이다 [확인: 프로세스 트리, 호스트 6일째·앱 13시간째]. 엔진의 `/restart`(별칭 `/update`, "Restart on X and keep this session")는 기능 플래그 `tengu_fancy_wand`가 꺼져 있어 쓸 수 없다 [확인: `~/.claude.json`, 2.1.311]. 백그라운드 세션(`claude --bg`/`/bg` + `claude attach`, 문서 이름 agent view)은 자동 업데이트 때 쉬는 세션을 엔진이 알아서 새 버전으로 옮기지만 [문서], `claude respawn`은 진행 중인 명령과 답변을 끊고 이어가지 않으며 [확인: 실험 3회, 백그라운드 명령은 살아남음], 붙인 세션은 Orca가 세션으로 알아보지 못해서 [확인: 사용자] 버렸다.

- 상태 상자 막대(2026-10-27 사용자 요청, 테스트 통과, 화면 확인 전): 사이드바에서만 라벨을 4칸(`ctx `, `5h  `, `7d  `)으로 맞춰 세 막대가 같은 열에서 시작하고, 7d에도 막대를 붙였다. 막대 폭은 상자 폭에서 라벨 4칸·숫자 5칸(오른쪽 정렬 ` 45%`)·가장 긴 꼬리(5h의 `↻ 1h 30m`과 소진 예측, 7d의 `↻ 3d 4h`)를 뺀 값이고, 8~20칸. 사이드바에서는 7d에도 리셋까지 남은 시간을 붙이고, `↻`와 숫자 사이, 시와 분·일과 시 사이를 한 칸씩 띄운다(밴드는 `↻1h30m` 그대로, 7d 리셋 없음). 채운 부분은 지금처럼 굵은 선 `━` + 단계색, 빈 부분은 흐린 점선 `╌`(밴드는 `─` 그대로). 사용자가 점선이 최선인지는 확신하지 않았다: 다른 후보는 `─`(지금), `┄`. 밴드는 짧은 막대·7d 막대 없음 그대로.
- 상태 상자 색(2026-10-27 사용자 요청, 테스트 통과, 화면 확인 전): 사이드바에서만 사용률을 다섯 단계로 칠한다. 여유 0–49% 초록(`success`), 보통 50–69% 노랑(`warning`), 주의 70–84% 주황(`claude`), 위험 85–94% 빨강(`error`), 한계 95%+ 빨강 + 숫자 뒤 `!`. 막대와 숫자 모두 늘 색을 칠하고, 주의부터 굵게. 7d는 속도도 본다: 지금까지의 속도로 리셋 때 닿을 값(사용% × 7일 ÷ 지난 시간)이 85% 이상이면 주의, 100% 이상(리셋 전에 바닥)이면 위험, 130% 이상이면 한계까지 올린다. 첫 하루는 조금만 써도 빨라 보여서 퍼센트만 보고, 리셋 시각이 없을 때도 그렇다. 속도 때문에 올라간 것인지는 따로 표시하지 않는다. effort 값은 단계별 색: low 흐림, medium 기본 글자, high 파랑(`suggestion`), xhigh 보라(`merged`), max 보라 굵게. 경고색(노랑~빨강)은 쓰지 않는다. 세션 고정이어도 단계 색이고 `(세션)`으로 알린다(밴드는 청록, 세션 고정이면 노랑 그대로). 상태 상자 테두리를 effort 색으로 칠하는 안은 사용률 경고색과 뜻이 겹치고 상자 하나만 튀어서 하지 않았다. 밴드는 터미널 16색에 주황이 없어 세 단계(60% 노랑, 85% 빨강) 그대로.

점검에서 나왔지만 고르지 않은 것(나중에 다시 볼 수 있음):
- 작업 상자를 장비 상자의 고양이 옆으로 합쳐 "지금" 상자로(쉬는 동안 `· 대기 중` 한 줄에 3줄을 쓰고, 고양이가 같은 상태를 보여 준다). 장비 정보는 한두 줄로.
- 상태 상자의 5h·7d를 한 줄로.
- 밴드 3줄 줄이기(대화의 답변 끝 요약 줄과 겹치고, 토큰·5h·캐시가 붙어 좁은 화면에서 잘린다).
- 확인 필요: 사이드바 테마 색 중 effort(`suggestion`)·실행 중(`permission`)이 실제로 어떻게 보이는지.

보류: 다른 프로젝트에서 `/setup`이 처음 `settings.json`을 쓴 직후 입력 줄 표시(`❯`)가 두 번 그려지고 밴드가 비어 보였다(2026-10-27, 스크린샷 1장). 설정 파일 변경으로 엔진이 설정·플러그인을 다시 불러온 탓으로 추정. 계속 남는지, `/setup`을 다시 실행해도(이제 쓰지 않음) 생기는지 미확인. 사용자가 일단 무시하기로 함.

### F10. likely (확률 판정)
2026-11-04 결정·MVP 구현, 테스트 통과, 실제 API 호출 전. 이름: 후보 decide·judge·maybe·verdict(앞서 jury·odds·tally·haikudge·augur) 등을 검토했고, decide는 OpenAI Decisions와 겹쳐서 피했다. 사용자가 likely를 골랐다(2026-11-04). 처음 커밋은 `/decide`였고 같은 날 likely로 바꿨다.
OpenAI Decisions·Jev처럼 입력 글 + 질문(predicate 예/아니오, choice 선택, score 단계) → 답 + 확률을 주는 범용 판정 기능을 Haiku로. 사용자 할 일 "haiku로 decision api 따라하기"에서 시작.
- 목적(사용자): (1) Max 구독의 월 $100 API 크레딧 활용, (2) 확률 붙은 판정을 직접 만들고 보정까지 실험. 처음엔 기록을 분석해 프롬프트·로직을 고쳐 새 버전으로 내는 "개발 개선", 일정 수준(기준은 데이터 보고 정함)을 넘으면 기기에서 자동 보정만.
- 위치: hubblerc 안, 코드는 `hooks/likely/`에 모음(나중에 떼어 낼 수 있게). `method.ts`(질문·섞기·프롬프트·응답 읽기·평균, 순수), `cost.ts`(가격·하루/주기 합계·상한, 순수), `record.ts`(비밀 가리기·기록 줄·통계, 순수), `likely.ts`(키·호출·합계·기록 쓰기, 엔진), `bash-fail.ts`(첫 사용처), `command.ts`(`/likely`). 세션 밖(명령줄 도구)에서도 쓸지 미정.
- 함수: `likely($, { task, input, questions, samples = 5, thinking = false, meta? })` → `{ id, answers, raw, calibrated: false, samples, model, latencyMs, costUsd, tokens, methodVersion, logPath? }`, 판정하지 않으면 `{ skipped: 'no-key' | 'daily-cap' | 'budget', reason }`, 호출이 모두 실패하면 오류. 답 모양은 aitop100 `decide.ts`와 같다: predicate `{ probability, value }`(0.5 이상이면 예), choice `{ choice, confidence, probabilities: {값: 확률} }`, score `{ score: Σp·단계, label, confidence, probabilities: [{ label, probability, value }] }`(단계 번호는 0부터, confidence는 최대 확률), 모두 거절이면 `{ type: 'refusal' }`. `raw`는 호출별 분포(원래 보기 순서), 나중 보정이 여기서 맞춘다. 질문은 이름이 겹치지 않고, 보기·단계 2~20개.
- 모델·호출: `$.http.fetch('https://api.anthropic.com/v1/messages')`로 직접, 헤더 `x-api-key`(아래 키)·`anthropic-version: 2026-10-21`. 모델 기본 `claude-haiku-5-5`(설정 `likelyModel`로 바꿀 수 있지만 비용은 Haiku 5.5 가격으로 센다). 크레딧은 Console 조직 API 키 호출에만 적용 [공식 문서]. 환경 변수는 읽지 않는다: 이 프로세스의 환경은 모든 Bash 자식 프로세스로 넘어가 키가 샐 수 있고, `ANTHROPIC_API_KEY`는 Claude Code 자체가 그 키로 돌아 일반 사용이 유료 과금될 수 있다 [추정].
- 요청 모양(전부 [추정: claude-api 스킬 문서 기준, 실제 API로 확인 전]): temperature·top_p·top_k를 보내지 않는다(Haiku 5.5는 기본값이 아니면 400, 2026-10-21 버전은 값이 있으면 400). structured outputs `output_config.format = { type: 'json_schema', schema }`, 스키마는 질문과 상관없이 하나 `{ answers: [{ probabilities: number[] }] }`(보기 이름을 enum에 넣지 않아 스키마 컴파일 캐시를 같이 쓴다). effort `low`. thinking 끔 `{ type: 'disabled' }`(문서상 Haiku 5.5는 effort low·medium·high에서 받는다), 켬 `{ type: 'adaptive' }`(Haiku 5.5는 `{ type: 'enabled', budget_tokens }`가 400이고 생각 양은 effort로 정한다는 문서를 따름). 최대 토큰 끔 400, 켬 3000(thinking도 max_tokens를 쓴다).
- 확률(방식 버전 `METHOD_VERSION = 1`, 프롬프트·로직을 바꾸면 올린다): N회 병렬. 매 호출에서 질문마다 분포를 말로 받는다(predicate 예일 확률, choice 보기별, score 단계별). 호출마다 기호 묶음(A·a·1)을 무작위로, choice 보기 순서는 무작위로 섞고, score는 짝수 호출 낮은 단계부터·홀수 호출 높은 단계부터(척도가 척도로 남게 순서만 뒤집음), predicate는 홀수 호출에서 "아니오일 확률"로 묻는다(5회면 2회). 섞기는 판정 id에서 씨앗을 얻어 다시 만들 수 있다. 받은 값은 0~1 범위 검사(벗어나면 그 호출 버림) → 합 정규화 → 원래 보기 순서로 되돌림(부정형은 1−p) → 0.02~0.98로 자르고 다시 정규화 → N개 평균. 응답 하나가 모양이 틀리면 그 호출만 버린다.
- 실패: 일부 호출이 실패하면 나머지로 판정, 전부 실패면 오류(비용은 셈). 거절(`stop_reason: refusal`)은 호출에서 빼고, 모두 거절이면 refusal 답. 재시도·시간 제한은 없다(새 타이머 금지. `$.http.fetch`에는 시간 제한 옵션이 없다 [확인: 타입 문서]).
- 키: 읽는 순서는 (1) 플러그인 설정의 민감 항목 `anthropicApiKey`(`sensitive: true`, 보안 저장소. 비민감 항목만 `/config` 메뉴 행이 된다 [확인: reference.md]), (2) macOS 키체인 `/usr/bin/security find-generic-password -s hubblerc-likely -w`(계정 무관). 설정에 키가 있으면 키체인은 묻지 않는다. 키체인은 세션 시작 때 한 번 읽어 모듈 변수에만 두고(상태·store·기록에 넣지 않음), 항목 없음·거부·5초 안에 답 없음이면 조용히 없음. 키가 없을 때 `/likely`를 실행하면 키체인을 다시 읽어, 세션 중에 넣은 키도 다시 불러오기 없이 쓴다. 둘 다 없으면 판정하지 않는다(Bash 예측은 조용히 건너뜀, `/likely`는 넣는 법을 안내).
  - 넣는 법: 설치본(`hubblerc@hubblerc`)은 세션 안 `/plugin configure hubblerc@hubblerc`의 anthropicApiKey, 또는 키체인. 개발판(`hcc`, `--plugin-dir`)은 설치된 플러그인이 아니라 `/plugin configure hubblerc`에 likely 항목이 나오지 않고("Configuration cancelled" [확인: 사용자]) `claude plugin configure`도 설치본만 다뤄서, 키체인뿐이다. 키체인 명령을 외우기 어려워(2026-11-05 사용자) 셸 함수 `hubblerc-key`를 둔다(F8의 셸 파일, `/setup`이 깐다): 넣기·바꾸기 `hubblerc-key set`(가린 입력으로 묻는다), 지우기 `hubblerc-key delete`(y/N), 확인 `hubblerc-key`(있는지만, 값은 보이지 않음). 키를 바꾼 뒤 이미 키를 들고 있던 세션은 새 세션부터 새 키를 쓴다(키가 없던 세션은 `/likely` 한 번으로 읽는다).

## 개발 메모
- 로드(2026-10-26 바꿈): 마켓플레이스 `hubblerc`는 GitHub(`Circlewee/hubblerc`)이고 `hubblerc@hubblerc`는 사용자 범위로 설치돼 모든 프로젝트에서 켜진다. 이 저장소에서는 `.claude/settings.local.json`에서 배포판을 끄고(`"hubblerc@hubblerc": false`), `hcc` 별칭(`claude --plugin-dir ~/vault/project/hubblerc/plugins/hubblerc`, `~/.zshrc`)으로 디스크의 개발판을 띄운다 [확인: 이 폴더 disabled·다른 폴더 enabled, `--plugin-dir`로 `/setup` 실행됨]. `--plugin-dir`는 저장하면 자동 리로드된다고 문서에 있다. 로컬 마켓플레이스와 GitHub 마켓플레이스는 이름이 같아(`hubblerc`) 함께 등록할 수 없다. 다른 프로젝트의 배포판은 버전을 올리고 푸시한 뒤 `claude plugin marketplace update hubblerc` → `claude plugin update hubblerc@hubblerc --scope user`로 받고, 재시작하면 적용된다 [확인: 0.2.1 → 0.2.2]. 자동 갱신 여부는 미확인.
- 검증: `claude plugin validate plugins/hubblerc`, 테스트는 `claude plugin test plugins/hubblerc`
- 타입 검사: `bunx -p typescript@5.6.3 tsc -p plugins/hubblerc`. 엔진 타입 정의는 git에 넣지 않으므로, 새 기기에서는 plugin-authoring 스킬이 만든 `claude-code.d.ts`를 `plugins/hubblerc/.claude-plugin/types/claude-code/index.d.ts`로 복사한다.
- 규칙: `read`/`update`에 넘기는 atom은 그 파일 안의 `const`로 `atom(...)` 해야 한다. 다른 파일에서 import한 atom은 validate가 거부한다.
- 커맨드 출력 앞에는 엔진이 플러그인 이름(`hubblerc:`)을 붙인다. 출력 문구에 이름을 또 넣지 않는다.
- 테스트 키트(2.1.317)는 `$.session.root`·`$.prompt.suggest`를 구현하지 않는다("no implementation for session.root") [확인]. 2.1.318 키트는 `$.prompt.read`·`$.prompt.fill`도 구현하지 않는다(2026-11-05, 대역 없는 시험 mod로 확인: "no implementation for prompt.read"). `tests/engine.ts`의 대역이 이것들과 `$.tool.register`(등록 내용을 기록)를 받는다(입력창은 `promptBox`, fill은 `insert`면 커서 위치에 끼우고 커서를 옮김, `isFillTaken: false`면 거절). 플러그인이 등록한 도구는 테스트에서 `$.tool.call({ tool: 'mcp__hubblerc__user_todos', … })`로 부른다.
- 테스트 키트의 `find({ key })`는 `Text`의 key를 찾지 못한다(Box·Button은 찾는다) [확인: 2.1.317]. Text는 글자로 찾는다.
- 2.1.318 테스트 키트의 `$.ui.resolve(e)`는 표면과 상관없이 모든 요소(Input·Select·Image·Raster·Svg·Client 포함)를 돌려준다 [확인: 2026-11-04, terminal·desktop·vscode·mobile 모두 같은 12개]. 테스트는 `ui.resolve`를 가로챌 수 없다(테스트의 `on('ui.resolve')` 훅이 효과 없음 [확인], 타입 문서도 엔진이 일으키지 않는 이벤트라고 함). 그래서 "어느 표면에 어떤 요소가 없음"은 테스트로 확인할 수 없다.
- 타입 정의는 `tool.call` 매처의 `tool`에 내장 도구 이름과 정규식만 받는다. 등록한 도구 이름 문자열은 그 기기에서 mod가 한 번 로드돼 `claude-code-mcp` 타입에 들어간 뒤에야 통과하므로 정규식(`/^mcp__hubblerc__user_todos$/`)으로 건다. validate는 정규식 매처를 받는다 [확인].
- 테스트 파일 쪽 `$`(테스트 훅이 받는 `$`)는 `$.store`를 부를 수 없다("its hooks module does not call it (host rule)") [확인: 2.1.318]. 플러그인의 store를 쓰는 함수는 플러그인 경로(명령, 도구 호출)로 시험한다. 테스트 훅은 테스트가 `$`를 처음 부르기 전에 걸어야 한다(뒤에 걸면 TypeError). 키트의 `expect`에는 `toBeCloseTo`가 없고, `Engine`에는 `$.state`가 없다(상태는 그린 화면에서 찾는다).
- `claude plugin test`는 파일을 고를 수 없다. 기계 부하가 높으면(load average 100 넘음, 다른 작업 동시 실행) 기존 테스트도 5초 제한에 수십 개씩 걸린다 [확인: 2026-11-04, 변경 전 코드도 46개 실패]. 부하가 내려간 뒤 다시 돌린다.
- `tsc`는 기존에 오류 3개가 있다(`sidebar.tsx`의 `Image` `source`, `device.test.tsx`의 `fs.list` 대역에 `mtimeMs`·`isLink` 없음) [확인: 2026-11-04, 판정 작업 전 HEAD에서도 같음]. 새 기능은 "새 오류 0"으로 본다.
- `userConfig`의 `sensitive`·`min`·`max`는 validate가 받는다 [확인: 2.1.318].
- 2.1.318 테스트 키트는 플러그인의 `$.ui.focus`를 테스트의 `on('ui.focus')` 훅에 넘기지 않는다(훅이 불리지 않고 "no implementation for ui.focus") [확인: 2026-11-05]. 그래서 키보드 이동 자체는 테스트로 흉내 낼 수 없고, `ui.open` 인자·순서와 `ui.panes`의 `isFocused`, 실패 때의 `/todo` 디버그 줄로만 검증한다. 테스트 파일 쪽 `$`는 `$.ui.focus`도 부를 수 없다(host rule).
- `claude plugin validate`는 `skills/<이름>/SKILL.md`도 검사하지만 문제가 있는 스킬만 출력한다: frontmatter YAML이 깨지면 오류(실행 때 메타데이터가 버려진다고 함), frontmatter가 없으면 경고. 이름이 규칙에 안 맞거나(`Bad Name!`) 설명이 2,000자여도 아무것도 나오지 않았다 [확인: 2026-11-05, 2.1.318, scratchpad 시험 플러그인]. 그래서 hubblerc 출력에 스킬 줄이 없으면 정상으로 읽힌 것이다.
- 같은 테스트 파일에서 앞 테스트가 채운 모듈 변수가 다음 테스트에 남지 않았다 [확인: 2026-11-05, 2.1.318, 지금은 지운 aside 규칙 테스트의 있음 → 없음 순서].

## 실행해서 확인한 사실 (2.1.308)
- "… for Ns" 줄(`TurnDuration`)의 `e.requestId`는 그 줄의 대화 기록 행 uuid와 같다. `session.append`(door `notice`, `message.name === 'turn_duration'`)에서 그 uuid를 턴에 저장해 두면 줄과 턴을 정확히 짝지을 수 있다.
- 엔진이 그 줄에 표시하는 시간은 틀릴 수 있다. 백그라운드 서브에이전트를 띄운 뒤의 답변은 이전 질문의 시작 시각부터 잰다(14초 답변이 23분으로 표시됨). `turn.complete`의 `durationMs`는 맞다. 그래서 시간으로 짝짓는 것은 예비 수단으로만 쓴다. 엔진 버그로 보고함(/feedback).
- 백그라운드 서브에이전트는 띄운 턴이 끝난 뒤에도 도구를 쓴다. Agent 결과의 `agentId`로 띄운 턴에 붙인다. `SubagentHandback`은 엔진 내부 호출이라 세지 않는다.
- 크로스 세션 메시지로 시작된 턴의 `turn.start` 텍스트는 `Another Claude session sent a message:` + `<cross-session-message …>` 태그로 감싸져 있다.
- Bash 호출 1,995건(최근 기록 29개) 모두 `description`이 있었다. 그래서 haiku 예비 요약은 아직 넣지 않았다.
- 이 환경의 세션에는 할 일 도구(TodoWrite, TaskCreate/TaskUpdate)가 없다. 밴드의 할 일 표시는 테스트로만 확인했다.
- `settings.read` 이벤트의 결과는 병합된 설정 객체 전체이고, `{ key }` 읽기는 그 객체에서 꺼낸 값이다.
- 같은 이벤트에 매처 없는 훅은 모듈 전체에서 하나만 등록할 수 있다(validate가 거부). 그래서 `session.start`, `turn.start`, `tool.call`, `turn.complete`는 `register.tsx`에서 한 번씩만 걸고 각 기능의 함수를 부른다.
- 테스트 키트의 `$`에는 `ui.close`가 없어서 "사람이 패널을 닫음"은 테스트로 일으킬 수 없다. `/panel`로 닫는 경로만 테스트하고, 사람이 닫는 경로는 실제 세션에서 확인한다.
- auto effort 측정(2026-10-26, 테스트 세션, Opus 5.5, 엔진 설정 xhigh). 실제로 보낸 effort는 기록 파일의 `api-request` 행 `params.output_config.effort`, 캐시는 응답의 usage에서 읽었다.
  - `turn.step`에서 바꾼 effort가 실제 API 요청에 그대로 나간다 [확인]. 슬라이더 수동 변경도 같은 경로다.
  - 판정: 간단한 질문 → medium, 한 줄 파일 만들기 → medium(예상은 high, 작은 작업이라 가볍게 본 것), 설계 검토 → xhigh, 직전 답변에 대한 짧은 정리 요청 → medium.
  - 캐시: effort가 바뀐 직후 요청의 캐시 읽기 비율이 96%(xhigh→medium), 99%(medium→xhigh), 96%(xhigh→medium)였다. 쓰기 분량은 새 메시지 크기 정도라, effort를 바꿔도 프롬프트 캐시는 깨지지 않는다 [확인: 3건].
  - 지연: 메시지부터 첫 API 요청까지 auto 전 0.07~0.13초, auto 후 0.78~3.09초(4건, 평균 약 1.5초). 판정 호출 시간이 그대로 더해진다.
  - 대기 상한을 2.5초로 줄이고 직전 답변 조회를 없앤 뒤 재측정(3건): 0.77~1.38초(평균 약 1.0초, 1.38초는 리로드 직후라 대화 기록을 읽은 경우). 3건 모두 상한 안이라 auto로 나갔다. 표본이 적어 개선 폭은 확정하지 않는다. 판정은 간단한 질문 → medium, Read+Edit 수정 → high, 대안 2가지를 짧게 제시하는 설계 질문 → high(예상 xhigh). 캐시 읽기는 effort가 바뀐 직후에도 99%.
- 밴드 훅이 `next(e)`로 넘기면 테스트에서는 아래에 그릴 것이 없어 오류가 난다. 테스트에서는 빈 `Box`를 그리는 대역을 둔다.
- 엔진은 파일을 바꾸는 Bash(`touch`)까지 Read, `ls`와 함께 한 줄로 접는다("Read 1 file, listed 1 directory, ran 2 shell commands"). Bash 용도는 `ToolUse` 행과 `ToolGroup` 줄 양쪽에 붙여야 보인다.

## 테스트 방법
- 같은 폴더에서 Claude 세션을 하나 더 열어 테스트 세션으로 쓴다. 개발 세션이 SendMessage로 "시나리오 N · …" 메시지를 보내고(`notify_when_idle`), 테스트 세션은 적힌 도구만 쓰고 끝에 `실제: …`를 적는다.
- 정답은 테스트 세션의 기록 파일(`~/.claude/projects/<폴더>/<세션 id>.jsonl`)의 도구 호출과 `turn_duration` 행에서 뽑고, 화면 쪽은 `/activity` 출력과 대조한다.
- 코드를 고치면 테스트 세션에서도 `/reload-plugins`를 해야 한다.
